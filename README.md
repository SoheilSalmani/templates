# Templates

Weft templates, one directory each. `base` is the root every repository starts from; the stack templates (`java`, `fastapi`, `dbt`, `airflow`, `scala`, `slides`, `cube`) extend it and add their own stack.

The templates need a `weft` built from source at the `WEFT_REF` of `.github/workflows/check.yml` or later. The 0.1.0 release ignores the `[refine]` tables and rejects the hooks' `before` field, only builds from `116e293` on can `weft patch amend` base's `mcp`, and only builds from `3751f9e` on can commit from a `weft session adopt --scope`, which the extracting-weft-templates skill teaches.

## Setup

```sh
mise install
```

## Starting a project

`weft new` renders a template into a new directory, asking the template's questions on the way. Give it a directory of this checkout, or the repository on GitHub without cloning it:

```sh
weft new gh:SoheilSalmani/templates//slides my-talk
```

Each template's `AGENTS.md` lists its questions and patches. A deck from `slides` opens on a tour of what it can do: its `docs/how-to-write-a-talk.md` turns that into your talk, and its README is the reference for the syntax.

For a client's repository, answer no to the `commit_*` questions: the skills, MCP configuration, `mise.toml` and agent instructions are still rendered and kept current by `weft update`, but the committed `.gitignore` keeps them, `paseo.json`, `.worktreeinclude` and `.weft/` out of git. `.worktreeinclude` then lists them, so Paseo and Claude Code copy them into each new worktree from the checkout it starts from; only the `.claude/skills/` links stay behind, since a failed copy aborts the worktree.

## The base template

Every stack template declares `extends = "../base"`, so base's questions, patches and hooks are part of it under their own names and ids: one change to base reaches every template and, through `weft update`, every scaffolded project. Change shared scaffolding in `base` only; `weft patch amend` refuses an inherited patch in a stack.

Base installs only the Agent Skills that depend on a choice the project makes. A tracker's skills work through the MCP server the project declares, so `linear` comes with `use_linear` and `jira` with `use_jira`; a stack's skills carry house rules the project opts into. Every other skill reads the same in any repository, so it lives in the owner's dotfiles under `~/.agents/skills` and never in base as well: the general ones (commits, history rewrites, records and decisions, documentation, agent instructions, CLIs, diagrams, work orchestration), the forge skills, the Weft skills, and the personal ones, with the `anki` and `obsidian` MCP servers they call. A skill in both scopes is shadowed or listed twice: Claude Code runs the personal copy over a project skill of the same name, Codex lists both, and oh-my-pi lists the home copy under a prefixed name. `skills` installs no skill: the skills patches depend on it, and its `sync-claude-skills` hook links each skill under `.agents/skills` into `.claude/skills` for Claude Code. The ones for one stack are behind the `stack_skills` question: `dbt-skills` behind `dbt`, `lightdash-skills` behind `lightdash`, `writing-slides` behind `slides`, and `terraform-skills` behind `terraform`. A stack narrows base's questions with `[refine.<id>]` tables in its `weft.toml`: dbt selects its skills and offers Lightdash's, slides fixes its own (its features extend `writing-slides`), and the other stacks offer none. No stack template is written for Terraform yet, so a Terraform repository starts from base with `terraform` in `stack_skills`. The same tables reword a question for the stack, such as `project_name`'s description.

The forge is two bools that exclude each other. `use_github` defaults to true; `use_gitlab` is asked only when it is false, and `gitlab_mcp_url`, the GitLab instance's whole MCP endpoint (`https://<host>/api/v4/mcp`, GitLab.com's by default), only with `use_gitlab`. A gated-off question keeps its default even when answered, so a project that answers both true gets GitHub alone. They choose the forge's MCP server and nothing else: the forge skills in the dotfiles carry both forges' mechanics, and each one's `references/forge.md` sends the agent to GitHub's or GitLab's by the host of `origin`.

`lightdash-skills` is generated by the Lightdash CLI's `install-skills` at the version its command pins, which `dbt`'s `lightdash` patch pins in `mise.toml` too: bump both, then run `weft patch resync lightdash-skills` in base rather than amending it.

`cube` pins one Cube release in four places: `compose.yaml` in `cube`, the Dockerfile in `image`, the chart's `appVersion` in `helm`, which also picks the Cube Store image, and the `cube` CLI in `cube-cloud`'s `mise.toml`. Bump them together with `weft patch amend`; a scaffolded project's `mise run chart:lint` fails when the first three disagree. The README of `cube` carries hand-written `expr` segments on `commit_mise`, which `weft patch amend cube` would flatten, so change that patch's README in its JSON, then run `scripts/check-templates.sh`. Its tasks are mise file tasks in `.mise/tasks/`, and its golden queries ship without their SQL snapshots, which each project's `mise run check` writes in the dialect of its own data source.

A stack's first patch, named after the template, builds on base's root: it adds each of the stack's ignore blocks to base's `.gitignore` where its tool sorts among base's blocks, replaces base's README where the stack has its own, and orders its setup hooks `before` base's `git-commit`, so the first commit includes what they produce. Every ignore file the templates write is a list of blocks, each headed `# Label (Tool)` with the name the tool's own docs give those files, sorted by tool.

Base's MCP files are shared. `mcp`, which `weft share` wrote, creates `.mcp.json`, `.codex/config.toml` and `.omp/mcp.json` around a slot, and each server is a patch that fills it: `github-mcp` when `use_github`, `gitlab-mcp` when `use_gitlab`, `jira-mcp` when `use_jira`, `linear-mcp` when `use_linear` and `notion-mcp` when `use_notion`. A file stays out of the project while no server fills it. `github-mcp` authenticates with a token each person exports, `GITHUB_PAT_TOKEN`; the entries name the variable, never the value. `gitlab-mcp` points at the `gitlab_mcp_url` answer, and each person authorises it with OAuth through dynamic client registration (`/mcp` in Claude Code, `codex mcp login gitlab` in Codex), like the Linear, Atlassian and Notion servers. A stack adds a server the same way: record it in a session on `mcp`, typing the entry where its patch name sorts, and commit with `--depends-on mcp`. `weft share` takes only files that several patches create, so a stack still reaches base's `.gitignore`, `.gitattributes`, `mise.toml` and `paseo.json` with hunks.

To change a skill base installs, amend the patch that installs it, under the skills recording name that `SKILLS_RECORD_ANSWER` sets in `scripts/lib.sh`; a skill from the dotfiles changes there. Skills get a recording name of their own because a skill that quoted `Demo Service` in an example would, recorded under it, carry answer references; for the same reason, no skill may quote the recording name. For the Linear skills:

```sh
cd base
weft patch amend linear --answer "project_name=Skills Recording"
```

A gated patch also needs the answer that switches it on, such as `--answer use_jira=true` for `jira`, or `--answer stack_skills=terraform` for `terraform-skills`. A skill writes GitLab's endpoint as `https://<host>/api/v4/mcp`: a recording abstracts `gitlab_mcp_url`'s default wherever it meets it, even with the question gated off, so a skill quoting GitLab.com's endpoint would carry an answer reference, which `check-templates.sh` fails. That is why the question takes the whole URL rather than the host, which every `docs.gitlab.com` link would contain. Edit the skill in the worktree the command prints, run `weft commit` there, then check every template.

```sh
scripts/check-templates.sh   # weft check every template under base's answer combinations, fail any skills patch that carries an answer reference, then prove the commit_* answers on a real render
```

CI (`.github/workflows/check.yml`) runs `check-templates.sh`, with `weft` built from source at the release or commit its `WEFT_REF` names.
